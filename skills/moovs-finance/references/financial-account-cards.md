# Financial Account cardholder and card coaching

Reviewed 2026-10-16 against the public July/August 2023 Financial Account guides.
These are dated, conditional workflows, not proof of current enrollment,
plan inclusion, card availability or today's exact verification screens.

## Access and private handling

The getting-started guide describes a beta request, private onboarding verification
and separate dashboard access. Ask Moovs Support for the current supported process
if access is not established; do not promote the historical beta contact as a
current offer. Existing provisioned access need not be reconfirmed for each step.
Core subscription, Moovs Payments and this separate Financial Account are not
interchangeable entitlements.

Apply task-authority.md in the approved dashboard: ordinary navigation and
non-sensitive holder selection can be executed; activation, issuance and orders
require exact current target/effect/terms approval. The owner logs in privately.
Pause inspection for identity/bank/card entry, verification and secret-revealing
issuance results. Never request credentials or raw financial identifiers in chat
or screenshots. Resume only on a non-sensitive view; unobserved private outcomes
are owner-reported. The checks below are recommendations, not observed state.

## Create a cardholder

1. In the separate Financial Account dashboard, have the operator open
   **Cardholders > Create a Cardholder** and choose the approved **Individual**
   or **Company** type. A Moovs booking contact is not automatically a cardholder.
2. The operator privately completes the currently required information, reviews
   the intended type/person or company, then selects **Save**. The public guide
   does not enumerate those fields; do not invent identity/verification requirements.
3. Have them return to Cardholders and confirm the intended entry exists and its
   displayed state. Creating/saving the holder is separate from activation and
   card issuance; stop there if only creation was requested.

## Activate an existing cardholder

1. Have the operator locate the intended existing holder in **Cardholders**,
   open its name and choose **Activate Cardholder**. Review the intended holder
   privately before starting; do not create a duplicate to work around an issue.
2. They follow the offered activation instructions privately. The source does not
   document every verification field, error or recovery route. Unclear requirements
   need the supported provider/Moovs process, not invented answers or repeated attempts.
3. Ask only whether the intended holder is shown as activated, pending or unclear,
   using the actual displayed state. Do not infer activation from starting the flow.
   An activated holder is required before creating a card; it is not an issued card.

## Create a virtual card

1. With the intended holder already activated and issuance authorized, have the
   operator open **Cards > Create a Virtual Card** and select that holder.
2. They review and complete the offered issuance flow privately. Do not invent an
   extra confirmation, spending-limit editor, fee, validation rule or issuance SLA.
   Stop if the actual flow is unsupported or the intended holder is unavailable.
3. The guide says completion displays card details. Keep the assistant away from
   that screen; never request or repeat those details. Ask for a non-sensitive
   report that the intended holder's card was created, or the actual pending/error
   state. Do not make a purchase to test it or infer unlimited spending authority.

## Order a physical card

1. Have the operator open **Cards > Order Physical Card** and choose the intended
   activated holder. This is an issuance/order task, not a customer card payment.
2. Complete only the approved delivery information in the private workflow; no
   unnecessary addresses in chat. Before submission, establish exact holder,
   destination, order and displayed terms approval; do not invent fees/delivery times.
   Pause for any sensitive verification or personal signature.
3. Have them check the actual order result for that holder before considering a
   retry. An order/request confirmation is not delivery, physical-card activation
   or a successful purchase. The reviewed guide does not establish later tracking,
   cancellation/reissue or physical-card activation controls; use current Support
   for those tasks rather than inventing a lifecycle.

## Do not silently change payout routing

The older onboarding guide uses **Settings > Payments** to add a Financial Account
with its account/routing details. A separate instant-setup article uses the unusual
label **default currency** for selecting that account. These are bank/payout-routing
changes, not cardholder/card prerequisites to perform automatically. Keep them a
separate authorized private workflow; verify the current supported destination and
meaning before changing a default. Card creation/order does not prove funds were
transferred, the account is funded, or an instant payout was enabled or received.
